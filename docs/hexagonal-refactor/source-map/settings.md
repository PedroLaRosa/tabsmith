# Source map: src/settings.rs (at af1b304)

## Behaviour traps
- Windows empty-USERPROFILE: L12-14 `var_os(USERPROFILE).or_else(|| var_os("HOME")).filter(|h| !h.is_empty())`. The filter runs after or_else, so USERPROFILE="" (set but empty) does not fall back to HOME; it errors. A rewrite as filter-then-or_else changes this. On Unix, both lookups read HOME.
- Different error strings: home() L15 says 'could not determine the home directory (set HOME or TABSMITH_HOME)', user_home() L25 says 'could not determine the home directory'. print_error prints them as `error: {err:#}` (cli.rs:899-901).
- TABSMITH_HOME and TABSMITH_SETTINGS_PATH count as unset when empty (L9 and L29 `.filter(|h| !h.is_empty())`). Both are used raw, with no canonicalize, so relative paths stay relative. var_os keeps non-UTF-8 paths; std::env::var would turn them into errors.
- settings_path L29-31 returns the TABSMITH_SETTINGS_PATH override before calling home(), so the `settings` commands work with no HOME. state_path L36 ignores the override. A DataDirectory that computes settings_file = root.join("settings.json"), or that resolves its root first, breaks both.
- Env is read lazily on every call. Commands that never touch home (--help, completion) never fail on a missing HOME. Building DataDirectory eagerly in bootstrap/SharedDependencies would turn that into a startup error.
- Store::load L49 `s.trim().is_empty()`: a whitespace-only file loads as an empty map. A UTF-8 BOM is not whitespace, so it reports 'corrupted'. L56: NotFound loads as an empty map. Other io errors get the context 'reading {path}'.
- Exact error text: L51 '{path} is corrupted' + serde cause (rendered '{path} is corrupted: expected value at line 1 column 1' via {:#}); L54 '{path} is corrupted (not a JSON object)' with no cause; L90 'writing {self.path}' names the link path, not the canonical target. L77 create_dir_all and L83 write have no context (bare io error). A non-anyhow error type in shared must reproduce this Display chain.
- Store::save L76-77 uses create_dir_all: it creates a missing data root (the test at L426-432 asserts this, 'settings commands create a missing data root'). Path::new("settings.json").parent() is Some(""), and create_dir_all("") is Ok. integrations::write_private (integrations.rs:518) uses create_dir, which fails on "", and on a missing grandparent by design. A unified AtomicFile must keep both modes.
- Store::save L79 canonicalizes and falls back to self.path on error. A dangling symlink therefore gets replaced by a regular file. L80 builds tmp as `target.with_extension(format!("tmp-{}", pid))`, which replaces .json (settings.tmp-123), in the target's directory, so the rename stays on one filesystem. A tmp file next to the link would break dotfile repos on another mount.
- Store::save L84-88: chmod 0600 runs after the write, and the error is ignored (`let _ =`). Save still succeeds on filesystems without chmod, and an existing target's mode is always replaced by 0600 through the rename. write_private instead opens with mode 0600 and chmods the parent to 0700 with `?` (integrations.rs:528). Unifying on that would chmod ~/.tabsmith, or the dotfiles dir behind a symlinked settings file, to 0700, and would make chmod failures fatal.
- Store::save L81-82: to_string_pretty (2-space indent) plus a trailing newline; an empty map writes "{}\n". Keys come out sorted because serde_json has no preserve_order feature (Cargo.toml:18), and nested objects such as inline.profiles.* are sorted too.
- Map ordering is behaviour. with_prefix L151-153 iterates sorted keys, and keys.rs:419-425 'a later binding for the same key replaces the earlier one'. So when two aliases of one keystroke are set, the alphabetically later one wins. cli.rs render_list depends on sorted order ('serde_json's Map is a BTreeMap'). SettingValue::Object and the Settings map must be BTreeMap, not HashMap or insertion-ordered.
- Integer vs float is behaviour. i64() L128 uses Value::as_i64, which returns None for floats (e.g. 49.0, 1e3) and for u64 above i64::MAX, so those fall back to the default: `inline.historyCount: 10.0` gives 49 (engine.rs:155), and `inline.debounceMs: 1000.0` gives 300 (pty.rs:880). f64() L132 accepts integers. inline parse_profile uses as_u64 for max_tokens, so 64.0 is rejected (inline.rs:227-231). A SettingValue::Number(f64) breaks all of these. It also round-trips `settings autocomplete.height 5` to '5.0' on disk and in `settings KEY` output, and loses large-int precision.
- scriptTimeout is read through two getters: engine.rs:142-148 uses f64(...,5000.0/20000.0).max(0.0) as u64, and js.rs:209-215 uses i64(...,5000/20000).max(0). The value 7500.0 gives 7500 in the engine and 5000 in js. Both getters must stay distinct; they cannot collapse into one 'number from catalog default'.
- Typed getters fall back on a wrong type: bool L120 maps "true" (a string) or null to the default; string L124 returns None for non-strings, so inline.source=5 falls to 'history+specs' at inline.rs:185; str_list L139-140 drops non-strings silently and returns an empty Vec for a non-array.
- with_prefix L153: a key equal to the prefix yields ('', v). Callers then see an empty keystroke or profile name.
- Settings::load L101-108: any error, including a corrupted file mid-edit or no HOME, logs `settings: {e:#}` and returns empty Settings. The pty reload at pty.rs:1269-1278 then replaces the live settings with defaults; it does not keep the old snapshot. The strict callers (cli settings get/set/delete via Store::load(&path)?) fail instead, and refuse to overwrite a corrupted file. The repository needs both behaviours.
- Settings is shared via Arc (L97) and sent across threads (pty.rs:1278 EngineMsg::Settings). The domain VO must stay Send with a cheap clone (no Rc).
- Catalog order L180-344 is the `settings list --all` row order (cli.rs:258-262 iterates it unsorted). The plain row prints e.ty and e.default raw, e.g. `"most recent"` with its quotes, `[]`, `null`, `""`. The JSON form parses default with serde_json and maps a template '' to null (cli.rs:272). Typed defaults rendered back through a SettingValue(f64) would print 5000.0.
- L244 `if cfg!(windows) { "20000" } else { "5000" }`: `settings list --all` output differs by OS, and the Phase 0 capture is macOS-only.
- Template rows L308 'autocomplete.keybindings.<keystroke>' and L327 'inline.profiles.<name>' have default ''. A catalog default(key) must return None for them, and must not treat concrete keys like autocomplete.keybindings.control+r as matching a template.
- wildcard_match L352-371 works on chars (Unicode scalars), is case-sensitive and has no escape. `?` matches exactly one char, `*` matches any run including empty, and a pattern of only stars matches "". Backtracking resumes at the last star. A byte-based or regex rewrite changes non-ASCII and edge results.
- Phase 1.6 `save_keeps_a_symlinked_file` relies on std::process::id() in the dir name and cleans up with remove_dir_all, both first and last. It is cfg(unix) only.

## Plan gaps
- Phase contradiction: Phase 1.4 says 'The old settings::home() family is deleted in Phase 11' and each later phase switches its own callers, but Phase 2.5 says 'Delete settings.rs', and section 5.2 says shims never cross phases. home(), user_home() and settings_path() have callers in logger, inline, specs, render, types, integrations, cli, pty, parser and doctor that only switch in Phases 4-10. The plan must either move all of them in Phase 2, or name where the family lives from Phase 2 until Phase 11.
- user_home() is not placed. Section 4 shared lists only DataDirectory (tabsmith's home), and the glossary DataDirectory covers ~/.tabsmith only. user_home is a separate concept (the real HOME, used for ~ expansion in parser.rs:326 and specs.rs:193, and for dotfiles in integrations.rs:561) with its own error message.
- The DataDirectory VO, described as 'settings path fns + joins', loses the TABSMITH_SETTINGS_PATH override: settings_file is not root/settings.json, and it resolves without a root. It also hides the lazy env read. An eager SharedDependencies { data_directory } fails at startup when HOME is unset, where today only the commands that need home fail.
- anyhow rule vs shared adapters: section 1 allows anyhow only in infrastructure/cli, infrastructure/pty and bootstrap. JsonDocumentStore, AtomicFile and data_directory_from_env (shared/infrastructure) need a hand-written error type whose {:#} Display reproduces the context chains at L15, 25, 51, 54, 57 and 90 exactly. The plan does not say so.
- AtomicFile 'unifies Store::save, integrations::write_private, integrations::write', but the three differ: create_dir_all vs create_dir, follow symlink vs not, chmod-after-write ignoring errors vs open with mode 0600 plus parent 0700 with `?`. A literal unification changes file and directory modes or the missing-dir behaviour. The plan should state per-caller options (follow_symlinks, create_parents, dir_mode_0700, strict_chmod).
- Fitness test vs catalog test: catalog_keys_unique_and_defaults_valid uses serde_json (L445). Phase 2.1 says to move it with SettingsCatalog into domain, which the std-only domain rule forbids. The test must split (domain asserts plus infrastructure JSON-validity), or the fitness test must exempt cfg(test).
- 'Defaults come from the catalog' (Phase 2.2): catalog defaults are raw JSON literals, and domain cannot parse JSON without serde. Options are a hand-written std JSON-literal parser, a typed default next to the literal, or keeping the caller-supplied default param. The raw &'static str must stay for `settings list --all`. The plan does not say which.
- Phase 2.2 lists only 5 per-key default tests (height, width, inline.enabled, theme, inline.source). Other call-site literals are left unguarded if the default param goes: inline.debounceMs 300 (pty.rs:880), inline.historyCount 49 (engine.rs:155), scriptTimeout 5000/20000 via both f64 and i64 (engine.rs:144, js.rs:211), beta.history.mode 'off' (engine.rs:1046), insertSpaceAutomatically true (engine.rs:1079), and about 14 bool-false keys. doctor.rs:576 uses unwrap_or("") for inline.source; it is unreachable today, but a string() that returns the catalog default would change the semantics of string()==None at specs.rs:186 (devCompletionsFolder null).
- The glossary's SettingValue 'Number' is a single variant. Following it literally loses the as_i64/as_u64/as_f64 distinctions (see traps) and changes on-disk and printed values (5 becomes 5.0). It needs Int/UInt/Float, or the raw lexeme, kept through setting_value_json.
- The glossary's SettingKey 'Validated non-empty' is new behaviour. Today `tabsmith settings "" x` stores key "", and `settings ""` errors 'No value associated with '. SetSettingUseCase with SettingKey::new(key)? (canonical shape, section 1) would reject it with a different error. That is not pure restructuring.
- 'Same getter surface so callers switch mechanically' is not mechanical for get() and with_prefix(), which return &serde_json::Value today. inline::parse_profile (inline.rs:203-231, serde API, until Phase 7) and keys.rs:419 (v.as_str(), until Phase 8) would need a temporary SettingValue to Value bridge in Phases 2-8. About 7 test helpers that build Settings via from_map(serde Map) need an infrastructure fixture (keys.rs:667, menu.rs:524, inline.rs:653, engine.rs:1267, parser/tests.rs:892, specs.rs:483, cli.rs tests).
- SettingsRepository has a single `load` in the plan, but the code has two semantics: strict (cli commands; Store::load(&path)? refuses to overwrite a corrupted file) and lenient (Settings::load: warn + defaults, pty.rs:400 and 1274, doctor.rs:479). The trait or adapters must offer both, and the warn text 'settings: {e:#}' must be logged by infrastructure.
- Diagnostics CheckFixer 'settings repository reset' (section 2 bridges): today's fix at doctor.rs:407-414 copies to json.bak-<secs> and then calls std::fs::write(path, "{}\n"). That keeps the existing mode, writes through a symlink and is not atomic. Routing it through SettingsRepository::save (AtomicFile) changes the mode to 0600 and replaces the inode.
- state.json has no owning repository beyond recency: doctor.prompt-restart-terminal is written by integrations::mark_restart (integrations.rs:284) and read by doctor.rs:220 through Store::load_state. The plan places StateFileRecencyRepository only. The flag's reader and writer span shell_integration and diagnostics with no named port.
- save_recency (engine.rs:73-79) guards Store::save's create_dir_all by checking parent.is_dir() first. If AtomicFile defaults to creating parents, every state writer (mark_restart at integrations.rs:284 has no guard) keeps recreating a purged ~/.tabsmith. That is today's behaviour too, but the unification must not 'fix' it silently.
- logger ↔ settings cycle: logger.rs:46 calls settings::home(), and settings.rs:105 calls logger::warn. The plan resolves it only implicitly (logger moves to shared, Settings::load to an adapter); it should say so.
