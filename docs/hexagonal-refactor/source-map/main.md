# Source map: src/main.rs (at af1b304)

## Behaviour traps
- main.rs has no #[test], and no test parses `Cli`. The whole clap surface (names, aliases, hidden flags, arg names) is guarded only by the Phase 0 output capture, which lists `--help` of every command but not the aliases `install` (L59), `diagnostics` (L67), `internal` (L76) or the hidden `_ *` / `version` behaviour.
- Clap derives subcommand and flag names from Rust identifiers. Applying the plan's 'rename to glossary names' step to `Command`/`InternalCmd` variants or fields changes the CLI. `PreCmd` (L96) → `pre-cmd`, invoked by shell/post.zsh:52 and post.bash:24 as `_ pre-cmd --alias "$(builtin alias)"`. `Pty`/`shell` (L83-86) → `_ pty --shell`, used in shell/pre.ps1:21 and pre.sh:18. `ShouldLaunch`/`GetShell` → `should-launch`/`get-shell`. `verbose` (L37) → `-v/--verbose`; the short flag comes from the field's first letter. Rename the types, never the variants or fields, or pin them with `#[command(name=..)]`/`#[arg(long=..)]`.
- Doc comments on clap items are help text. `/// Customize appearance & behavior` (L44) and the others are the `about` strings, and variant order (L45-77) is the help order. Adding a `///` doc to `Cli` (L34, which has an explicit `about`), to `PreCmd.alias` (L97, undocumented today) or to a new `PtyArgs` struct changes `--help` output.
- Keep these attributes byte-for-byte: `#[command(name = "_", alias = "internal", hide = true, subcommand)]` (L76); `hide = true` on Version (L64) and Completion (L70), which keeps them out of help and clap_complete output; `#[arg(last = true)] cmd` (L88), so `_ pty -- …` works; `allow_hyphen_values = true` on `--alias` (L97), because alias dumps can start with `-`; and `ArgAction::Count, global = true` (L36).
- Order: `Cli::parse()` (L103) runs before `logger::init` (L108). Parse errors and `--help`/`--version` exit through clap (code 2 or 0, clap's own colouring) and are never logged; the logs dir is not touched. Switching to `try_parse` + anyhow would route them through `print_error` with exit code 1.
- `logger::init(if is_pty { "pty" } else { "cli" }, cli.verbose, !is_pty)` (L108): `_ pty` logs to pty.log and never mirrors to stderr, even with -v, so nothing is drawn over the user's screen. `_ pre-cmd`, `_ should-launch` and the rest log to cli.log. The check matches only `Internal(Pty)`. HEAD keeps this in `runs_pty()`.
- Error tail (L140-143): `logger::error(&format!("{err:#}"))` runs BEFORE `print_error`, and both use the alternate `{:#}` chain format. With -v (non-pty) stderr gets the logger line (`<ms> Error <sid> msg`) and then `error: msg`. print_error writes `\x1b[1;31merror:\x1b[0m` only when stderr is a tty (cli.rs:897-903). If it is reimplemented with shared terminal_style, `epaint("1;31", "error:")` is byte-identical, but nested bold()+red is not.
- Only Err prints and exits 1. Handlers return Ok(non-zero) silently: `should_launch_cmd` prints the reason and returns Ok(1) (integrations.rs:459-463); `get_shell_cmd` returns Ok(1) with no output (integrations.rs:472). Modelling 'don't launch' or 'no parent' as an Err in the new use cases would add `error:` on stderr and a cli.log entry, which the shell pre-scripts would see.
- `std::process::exit(code)` with an i32 (L139). On Windows, pty returns `exit_code() as i32` (pty.rs:1374, 1559) and NTSTATUS codes become negative; exit passes the full 32 bits through. Replacing this with `fn main() -> ExitCode` truncates to u8. On Unix the js atexit hook (js.rs:989-996, `libc::atexit(at_exit)` → kill_live_children) relies on a normal process exit, and the fallback relies on `exec` skipping atexit (pty.rs:103). Do not switch to `libc::_exit` or abort.
- `Ok(pty::run(shell, cmd))` (L131): the wrapper must never leave the user without a shell (pty.rs:43, the fallback at 100-123). If Phase 9's `run_pty_command(args, &TerminalSessionModule) -> anyhow::Result<i32>` builds modules or settings with `?` before or outside pty::run's catch_unwind/fallback, a missing HOME or a corrupt settings.json would print `error:` and exit 1 instead of exec'ing the plain shell. The shell's pre block `exec`s tabsmith, so the user's terminal would just close.
- The None arm uses `Cli::command().print_help()` (L113), which writes to stdout with clap styling and exits 0. `render_help()` + println, or clap's `arg_required_else_help`, changes the bytes or the exit code.
- Arms that need no data directory today: no-arg help, `version`, `completion`, `_ get-shell`, and `_ pty` (it reaches its fallback). `settings` works with only TABSMITH_SETTINGS_PATH set and HOME unset (settings.rs:29-34). `home()` fails with "could not determine the home directory (set HOME or TABSMITH_HOME)" (settings.rs:15), while `user_home()` fails with a different message (settings.rs:25). If bootstrap builds SharedDependencies/DataDirectory eagerly with `?` before dispatch, all of these change.
- `logger::init` swallows a missing home: `crate::settings::home().ok().and_then(|home| open_log(&home.join("logs"), name))` (logger.rs:47-49). It logs only under an existing data root (logger.rs:61-63), with dir 0700 and file 0600. When the logger moves to shared and switches to DataDirectory it must keep `.ok()` (never fail main) and the same TABSMITH_HOME > HOME/USERPROFILE order, without the TABSMITH_SETTINGS_PATH override.
- `env!("CARGO_PKG_VERSION")` (L124) and `#[command(version)]` (L31) must keep producing the same string. `name = "tabsmith"` (L30) fixes the bin name in usage and help regardless of argv[0]. completion also hard-codes "tabsmith" (cli.rs:754).

## Plan gaps
- The `settings` no-key branch prints the root help: `<crate::Cli as clap::Parser>::try_parse_from(["tabsmith", "settings", "--help"])` (cli.rs:176; HEAD cli.rs:170 now uses `crate::bootstrap::cli::Cli`). Phase 2's `settings/infrastructure/cli/settings_command.rs` would then import `crate::bootstrap`, a back-edge into the composition root that breaks 'settings → shared' and makes a cycle. The architecture test does not catch it: only the domain and application rules forbid `crate::bootstrap`. The plan does not say who renders this help. Building it from `SettingsArgs::augment_args` alone would change the `Usage: tabsmith settings` line and drop the global `-v`. Options: handle it in bootstrap, or inject a help printer.
- `Command::Debug(cli::DebugCmd)` (L74) and its sub-dispatch `cli::debug` (cli.rs:762-768) are not placed. They span terminal_session (key tester, debug shell) and diagnostics (logs), so they belong in bootstrap/cli.rs. Also, `DebugCmd::Shell { shell: Option<crate::integrations::ShellArg> }` (cli.rs:118) and `debug_shell` calling `crate::integrations::init_script(shell, When::Post)` (cli.rs ~850) make the planned `terminal_session/infrastructure/cli/debug_shell_command.rs` depend on shell_integration's CLI type and use case. terminal_session's allowed dependencies (§2) exclude shell_integration, and rule 3 forbids the use-case call. This needs a bridge or the handler must live in bootstrap.
- Section 4 lists `cli::completion, version, cli::print_error` for bootstrap/cli.rs but not `CompletionArgs` (cli.rs:107-111, holds `clap_complete::Shell`). HEAD moved it there, which is correct; the plan text should say so.
- The plan's main.rs line ('Cli::parse → logger init → bootstrap::run → exit code', §2 and §4) leaves out that the error path must stay in main: logger::error, then print_error, then exit(1). It also does not say that the exit must remain `std::process::exit(i32)` and not `ExitCode` (Windows codes, atexit).
- §1 says CLI handlers are `run_<command>(args, &<Module>Module) -> anyhow::Result<i32>`, and modules are built from `&SharedDependencies`. Nothing says the building must be lazy per arm or infallible. Building eagerly with `?` changes the behaviour of help, version, completion, `_ get-shell`, `settings` with only TABSMITH_SETTINGS_PATH, and `_ pty`'s fallback guarantee (see behaviourTraps).
- Contradiction about the legacy path functions that logger::init depends on (logger.rs:47 `crate::settings::home()`). Phase 1.4 says 'the old settings::home() family is deleted in Phase 11', and Phase 11.1 says 'Delete … the old path functions'. Phase 2.5 says 'Switch every crate::settings::* import. Delete settings.rs.' Also, moving the logger into `shared/` in Phase 1.3 while it still imports `crate::settings` breaks rule 4 (HEAD test bcbb07e: shared must not reference legacy modules). So in Phase 1 the logger must switch to `data_directory_from_env`, keeping the `.ok()` swallow and the env precedence.
- Phase 5 step 1 ('move verbatim, then rename to the glossary names') has no exception for clap-derived identifiers. Renaming `InternalCmd::PreCmd`/`Pty`/`ShouldLaunch`/`GetShell` or the fields `shell`/`alias`/`cmd`/`verbose` changes the CLI that the shell scripts call. The plan should state that clap variant and field names are frozen, or pinned with explicit `name`/`long`.
- If Phase 9 or 4 turns `InternalCmd::Pty { shell, cmd }` / `PreCmd { alias }` into tuple variants over module-owned `#[derive(Args)]` structs, to match the `run_<command>(args, …)` signature, the help output can change through struct doc comments or attribute placement. The Phase 0 capture should include `_ pty --help` and `_ pre-cmd --help`, or the fields should stay inline in bootstrap and be passed as primitives.
