# Source map: src/cli.rs (at af1b304)

## Behaviour traps
- Integer vs float: parse_value (209) keeps serde_json's int/float distinction ("5" → PosInt 5). If SettingValue::Number is f64 (the plan's own example uses Number(10.0)), `settings k 5` writes 5.0 to settings.json, `settings list` prints `k = 5.0`, and Settings::i64 (settings.rs:128, as_i64) returns None for floats, so the default is silently used. render_list_all json `default` (272) must print 40, not 40.0.
- Strict vs lenient load: every mutating command uses Store::load, which errors on a corrupted file (182 settings set/delete, 361 theme, 466/496 inline, 442/450 inline status/show). Settings::load (settings.rs:101) falls back to empty. If one SettingsRepository::load swallows errors, `tabsmith settings k v` on a corrupted file overwrites it with {k:v}: DATA LOSS.
- Get does NOT use catalog defaults: render_get (215) errors "No value associated with {key}" for an unset key even when the catalog has a default. A stored JSON null prints `null` in plain (Some(Null) arm 218), unlike unset. Json/JsonPretty print `null` for unset (216), so the use case must return Option and the presenter decides error vs null.
- render_get Plain vs JsonPretty: strings are raw in Plain (217) but quoted in JsonPretty (218). Non-strings are pretty in both, compact in Json (219).
- JSON key order comes from serde_json's BTreeMap Map (no preserve_order in Cargo.lock), so every json! object is alphabetical: list --all rows {default,description,key,type,value} (269-275), show-customizations rows (584-595), diagnostic sections env-vars,environment,tabsmith with rows sorted (617-623). A typed #[derive(Serialize)] struct would emit declaration order and change the output.
- diagnostic: TOML keeps insertion order and drops nulls (729). JSON sorts keys and KEEPS nulls (621). The same data gives different orders in the two formats.
- render_list_all plain (258-261) prints the RAW catalog literal: `"dark"` with quotes, `"most recent"`, `null`, and an empty string for templates. Value is compact JSON or empty. Template keys (`autocomplete.keybindings.<keystroke>`) are looked up literally, so always empty. Order is the CATALOG declaration order, not sorted. scriptTimeout default is cfg!(windows) "20000" else "5000" (settings.rs:244).
- removal_message (232) uses Debug `{one:?}` (Rust escaping, not JSON) for a single key, and `Removing:\n  - k` unquoted for several. It is printed BEFORE remove+save (197-201), so the message shows even if save fails.
- settings with no key: --delete bails "the argument '--delete' requires a <KEY>\n Usage: tabsmith settings --delete <KEY>" (172). Otherwise it prints help built from the ROOT crate::Cli (176), which includes the global -v/--verbose flag and the `Usage: tabsmith settings` prefix, and exits 0. Building help from SettingsArgs alone changes the text.
- Conflict check ordering: `(Some(_), true)` (184) runs AFTER Store::load (182), so a corrupted file reports `... is corrupted` instead of the --delete/[VALUE] conflict message. The no-key checks run after settings_path() (152) but before the load.
- settings_path() (152) honours TABSMITH_SETTINGS_PATH and needs no HOME. theme (351), debug shell (825) and debug logs (882) need home(). completion, diagnostic and version never touch home. A SharedDependencies/DataDirectory built eagerly in bootstrap that errors without HOME would break those commands.
- DataDirectory must not canonicalise or normalise: `theme --folder` prints dir.display() (354), and debug logs prints the log paths (884).
- open_settings: it creates the missing file ({}\n, 0600, parent dirs) BEFORE resolving the editor (284-290), so on Linux with no EDITOR the file exists after the error. A whitespace-only EDITOR counts as unset (293). Whitespace-split args (296). Exit code is 0/1 from status.success() (313), not the editor's code. Launch failure prints `could not launch the editor: <io>` through {err:#}.
- theme set: a custom `<name>.json` is tried FIRST (375), so a themes/dark.json shadows builtin dark in the CLI (banner printed), while the renderer ignores it (render.rs:71 `"" | "dark" => Theme::dark()`). ANY read error (permission, is-a-dir, bad UTF-8) falls through silently to the builtin/not-found branch. `theme ""` → error (not builtin), but the renderer treats "" as dark. Names are not sanitised (`../x` is joined).
- theme set output: custom → print!(banner) with a leading "\n" and trailing "\n\n" (378, 416, 428). Builtin → println! with no leading blank line (380). Not found → "'{name}' does not exist in {dir}" (382). Parse error context is "invalid theme file {path}" (377). Store loaded at 361 and saved after the banner is printed.
- theme show (362-371): unset → "dark" (literal, not catalog). String → raw. Non-string → pretty JSON (Settings::string would return None and print dark instead). Stored null → "null".
- parse_theme validation lives in serde types: `version` (333) and `theme` (335) are #[allow(dead_code)] but reject non-string/non-object values. Deleting them as dead code moves those keys into `rest`, where they are no longer validated. Serde error text contains the struct name ("expected struct ThemeAuthor"), so renaming ThemeAuthor changes the user-visible error. shade*/accent* check (343) applies to ANY top-level key with that prefix.
- theme_list (392-413): only extension exactly "json" (case-sensitive); directories named x.json are included (no is_file check); non-UTF-8 stems are skipped; builtin stems are filtered; byte-order sort; read_dir errors give builtins only.
- inline status (442): Settings::bool("inline.enabled", true), so a non-bool value reads as enabled. Messages "Inline is {bold}", "Inline enabled/disabled" in SGR 35, only when stdout is a tty, sampled once at 437.
- set_customization: only parse-valid profiles are selectable (498-502). A name matching an INVALID profile → "Customization not found" (517). Interactive None → remove inline.source, save, print unbolded "Customization unset" (508-510).
- choose_source: checks STDIN tty only, BEFORE printing anything (529). Rows go to stdout as `{i}) {n} - {d}`, then `{N+1}) None`, then print! prompt + explicit flush (546-547). Input `0`, out-of-range, empty or EOF → "No customization selected".
- render_sources plain: an invalid profile never gets " (selected)" (573), but in json it does carry `selected` (594). The " (selected)" mark is outside bold. PROFILE_EXAMPLE is shown only when there are no profiles at all (invalid ones count) (576). Json gets an extra "\n" (601) and print! is used (451). Valid-profile json has provider/model/base_url/api_key_env but NO max_tokens/effort.
- diagnostics env: empty values count as unset for the env() closure (641) but are KEPT in env-vars (671-678). env-vars keeps non-UTF-8 keys out, lossy values, prefix TABSMITH_ (case-sensitive) plus exactly SHELL/TERM/COLORTERM/ZDOTDIR/PATH (Windows `Path` is excluded), sorted by key.
- Username scrubbing (633-640) is a raw substring replace of "/{user}" and "\\{user}" (no segment boundary). It applies to cwd, cli-path, shell-path, shell-version, terminal and env-var values, NOT to version or os. USERNAME on Windows, USER elsewhere.
- shell-version (646-659) runs `$SHELL --version` with NO timeout and takes the first stdout line even on a non-zero exit. Routing it through process_runner/output_with_timeout would change behaviour. in-wsl is only on Linux (666). terminal falls back TERM_PROGRAM → WT_SESSION ⇒ "Windows Terminal" → TERM.
- to_toml (730-737): a bare key is [A-Za-z0-9_-]* (an EMPTY key counts as bare), else a JSON-quoted key. Values use serde_json Display escaping. The final trim_end, then println! adds exactly one newline (612).
- completion (749-757): buffered on purpose (clap_complete panics on a write error). A broken pipe returns Err, so print_error prints `error: Broken pipe` and exit 1.
- key_tester exits only when ONE read is exactly [0x04] (798) or EOF (793). It prints "ctrl-d" in BOTH cases (805). disable_raw_mode runs before `res?`, and its own error wins (803-804). The banner is printed before raw mode. Inside raw mode lines end with "\r\n".
- debug_shell: with no arg, Windows → Pwsh regardless of $SHELL (814); otherwise from $SHELL or the error "Could not determine current shell or shell not supported". exe is $SHELL only if it names the same shell, else shell.name() (821-823). post = init_script(..., Post)? + "\n", which reads TABSMITH_INIT_SNAPSHOT_TEST and current_exe through integrations.rs:196-209.
- debug_shell mutates PROCESS env with std::env::set_var (ZDOTDIR only for zsh, TABSMITH_DEBUG_SHELL=1) BEFORE pty::run spawns threads (827-830). If bootstrap builds modules that start threads first (recency saver, engine server), set_var becomes racy with getenv on Unix. Turning it into child-only env changes also changes what in-process readers and spawned generators inherit.
- debug_shell output uses `let _ = writeln!` and never println! (831, 835): the terminal may be gone and println! would panic. Guarded by debug_shell_survives_closed_terminal. Returns pty::run's code as Ok(code), and the rc dir is removed with errors ignored.
- debug_shell_files: DirBuilder recursive + mode 0o700 (851-855) creates home and run too if missing, all 0700. The rc file uses plain std::fs::write (umask mode, not 0600). Routing it through AtomicFile/write_private (0600 file, purge guard requiring the data root to exist, integrations.rs:513-) would change the modes and break a fresh home. prune_run_files deletes only files (is_file), so debug-shell-<pid> dirs survive. A generic prune_older_than must not remove dirs.
- debug_shell argv shapes are exact (866-877): bash `--noprofile --rcfile <rc>` (unquoted argv element); zsh only exe (+ZDOTDIR); fish `--no-config -C "set -q fish_color_autosuggestion[1]; or set -g fish_color_autosuggestion brblack; source <q(rc)>"`; pwsh `-NoProfile -NoExit -Command ". <q(rc)>"`. rc names: bashrc, .zshrc, post.fish, post.ps1.
- debug logs: always prints the cli.log and pty.log paths, even if missing (884). Only if pty.log is readable: a blank line, then the last 50 lines (lossy UTF-8; lines() strips \r). Logger: debug shell runs in the CLI process, so it logs to cli.log and mirrors to stderr with -v (main.rs:104-108 is_pty only for `_ pty`). Keep bootstrap's logger rule.
- print_error (897-903): `{err:#}` joins the anyhow context chain with ": ". Domain error enums wrapped at the CLI boundary must Display the same text (e.g. "{path} is corrupted: …", "invalid theme file {path}: …", "could not launch the editor: …"). Runtime errors exit 1 (main.rs:143). clap usage errors exit 2 before dispatch.
- Store::save bytes (settings.rs:75-92): pretty JSON, sorted keys, trailing \n, 0600, written through the symlink target. Every set/delete/theme/inline write goes through it, and JsonFileSettingsRepository must produce the same bytes. SettingValue::Object must be ordered (BTreeMap), or `settings inline.profiles.x` pretty output reorders.

## Plan gaps
- DebugCmd (113-123) and the debug() dispatcher (761-767) are not placed in §4. They span terminal_session (key-tester, shell) and diagnostics (logs), so the natural home is bootstrap/cli.rs. Must stay one clap enum (help order/text).
- debug_shell_command in terminal_session needs init_script(shell, When::Post) (824) and ShellArg (119), both shell_integration. The §2 dependency graph forbids terminal_session → shell_integration, and rule 3 forbids importing another module's infrastructure (ShellArg lives in shell_integration/infrastructure/cli/init_command.rs). No bridge for this is listed in the §2 bridges table. Needs a port (e.g. an integration-script source bridged in bootstrap), or the debug shell handler lives in bootstrap.
- settings_command.rs needs root-Cli help (176: <crate::Cli as clap::Parser>::try_parse_from(["tabsmith","settings","--help"])). After Phase 1 Cli lives in bootstrap/cli.rs, so a settings infra → bootstrap import creates a cycle. Help built from SettingsArgs alone loses the global -v and changes the text. Needs a callback or outcome from bootstrap. Phase 1 must also repoint 176 and 753.
- Phase 1 moves OutputFormat to shared, but integrations.rs:4 and :93 import crate::cli::OutputFormat. They must be switched in Phase 1 (a re-export shim in cli.rs would cross phases, against §5 rule 2).
- Glossary SettingKey is 'validated non-empty', but today `tabsmith settings "" v` stores key "" and `settings ""` prints "No value associated with " (no validation in 183-203). Validating in SetSetting/GetSetting changes behaviour, so it must be accepted or kept off the CLI path.
- Plan §4 (226-227) puts parse_value in setting_value_json.rs, but §5 Phase 2.4 moves 'settings render/parse tests' to settings_command.rs. settings_set_parses_json_or_string should follow parse_value. Similarly matching_keys is listed under settings_command.rs, though its logic belongs to DeleteSettingsUseCase/SettingKeyPattern, so settings_delete_wildcards must be split.
- The plan's SettingValue (Number only, example Number(10.0)) does not say it keeps int/float/u64 precision. Without that, set/list/i64 change (see traps). SettingDefinition with a typed default must still print the exact raw literal in `list --all` plain (empty for templates, `null`, `"most recent"`).
- 'One parser, not two' for themes (§4 line 373-374, Phase 8.4): cli parse_theme is a strict validator (errors on wrong types, does not check colours), while render::Theme::from_json is lenient (bad JSON → dark, bad colour → filler, v1 only if version=="1.0" and theme is an object). Merging them must keep both behaviours.
- 'BUILTIN_THEMES deduped with ThemeChoice' (§4 line 375): ThemeChoice (renderer) maps "" → dark and ignores themes/dark.json, while the CLI rejects "" and prefers dark.json. A single shared rule changes one of the two.
- type Section (608) is to become the DiagnosticReport/DiagnosticSection domain VO, but it carries serde_json::Value (forbidden in domain). The report needs a std-only scalar (Text/Bool/Missing), with to_toml and json kept in infra using the same serde_json Display escaping.
- diagnostics() (631-722) is pure I/O gathering, but §4 assigns it to diagnostic_command.rs alongside a CollectDiagnosticReportUseCase. No port is listed to feed that use case: system_facts_probe is doctor-oriented. Decide which port supplies the env snapshot, cwd, current_exe and the shell --version line.
- emit (141), selected_source (484) and provider_name (488) are not named in §4. provider_name is needed by both inline_command.rs (render_sources) and stdin_source_chooser.rs (choose_source), so it belongs on LlmProvider (domain).
- open_settings (282-314) is listed only as system_settings_editor.rs. Its create-if-missing step (Store::save of an empty map) is persistence and belongs to OpenSettingsFileUseCase via SettingsRepository. The order 'create file, then pick the editor' must be kept.
- The shared temp_dir replacement for tests::tmp_dir (913) changes names (unique suffix). debug_shell_rc_dir_and_quoting depends on the `'` in the path, so TmpDir::new("o'brien") must keep the tag verbatim. debug_shell_survives_closed_terminal hard-codes its own test path in const NAME (1197), which must be updated when it moves.
- debug_shell_files uses its own DirBuilder 0700 + plain fs::write (851-862) and is not in the AtomicFile unification list. Do not route it through AtomicFile/write_private: the purge guard needs an existing data root and the rc file mode would change.
- Bootstrap's SharedDependencies (§4 shared, Phase 1.4) must resolve DataDirectory lazily or per command. Today only settings/theme/inline/debug shell/debug logs read home or settings_path, and the TABSMITH_SETTINGS_PATH override needs no HOME.
