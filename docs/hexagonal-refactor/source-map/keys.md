# Source map: src/keys.rs (at af1b304)

## Behaviour traps
- Override precedence follows the order of Settings::with_prefix. Today that is serde_json::Map, which is a BTreeMap because serde_json has no preserve_order (Cargo.lock: no indexmap), so keys come in lexicographic order. Keymap::set (L435-437) replaces on duplicates, so when two user keys normalize to the same Key, the lexicographically last one wins: 'ctrl+x' beats 'control+x', 'option+x' beats 'alt+x', 'alt+k' beats 'alt+K'. Phase 2's new Settings must keep sorted iteration; a HashMap or insertion order would change which binding wins.
- A non-string value is skipped, not turned into Unknown: `let Some(v) = v.as_str() else { continue };` (L420). So "f5": 3 leaves f5 unbound, and the test asserts `b(b"\x1b[15~") == None` (L708). If SettingValue gets a stringifying accessor, "3" goes to from_id, returns None, becomes Binding::Unknown, the key is swallowed, and the test breaks.
- "ignore" is compared before from_id strips the prefix (L421-423). So "autocomplete.ignore" becomes Binding::Unknown (key swallowed), not Ignore.
- from_id uses `id.strip_prefix("selectSuggestion")?.parse::<u8>()` (L313). Rust's u8 FromStr accepts a leading '+' and leading zeros: 'selectSuggestion+5' and 'selectSuggestion05' both give SelectSuggestion(5); 'selectSuggestion256' and 'selectSuggestion0' give None. Do not swap in a digits-only check.
- parse_keystroke silently ignores unknown or miscased modifiers (`_ => {}`, L342): 'hyper+x' and 'Ctrl+k' both parse to a plain key (test L636). Key names are case-sensitive: 'Enter', 'ESC', 'F12', 'escape', 'return' and 'space' all return None and the binding is dropped (L432-434), so the default stays.
- The split loop (L333-347) treats `Some(("", ""))` as a literal '+'. 'ctrl++' gives ctrl+'+'; '+' and '++' give '+'; 'a+' and 'ctrl+' give None (L643). Keep the exact split_once loop.
- Fn keys parse with `f[1..].parse().ok()?` (L363-364). 'f0', 'f99' and 'f01' are accepted ('f01' is F(1)). 'f256' makes the whole keystroke None. 'f' alone is Char('f') (len>1 guard).
- shift+lowercase ASCII becomes uppercase and clears shift (L372-375): 'shift+a' is Char('A') with no mods (test L631). 'shift+A', 'shift+1' and 'shift+é' keep shift, and the decoder never produces those, so they never match. Keep it.
- normalize lowercases only when ctrl or alt is set (L385) and runs at both set and lookup. It must stay a keymap concern. Moving it into the decoder or Key construction would change pty::ghost_key, which matches `KeyCode::Char('f') if alt` (pty.rs L180): today alt+F ('\x1bF', decode_table L547 asserts Char('F') ALT) does not accept the next word.
- decode_one arm order (L126-131): \r, \n, \t, 0x7f/0x08 are matched before the `0x01..=0x1a` ctrl range. So ctrl+h is Backspace, ctrl+i is Tab, ctrl+j/ctrl+m are Enter, and ctrl+j can only be bound via CSI-u (test comment L710). 0x00 and 0x1c-0x1f give Unknown.
- UTF-8 (L132-147): a truncated or invalid sequence gives Unknown with length 1 and no carry-over across reads (only a paste carries state), so a char split over two reads becomes several Unknown events. The bytes are still forwarded exactly because every event has len>=1 and the ranges tile the chunk.
- SS3 (L165-180) always consumes 3 bytes, even when b[2] is the lead byte of a multibyte char ('\x1bO\xc3\xa9' gives Unknown(3) then Unknown(1)). 'ESC O' and 'ESC [' at chunk end (len 2) fall to the alt branch L182 and give alt+'O' / alt+'['.
- The ESC-ESC alt prefix needs `b.len() > 3` and b[2] in '[' or 'O', and not a paste start (L155-156). Otherwise the first ESC is a lone Esc of length 1 (L163). '\x1b\x1b[' (3 bytes) gives Esc, then alt+'['. An unterminated '\x1b\x1b[1;' gives Unknown with alt=true covering the rest of the chunk.
- CSI final 'R' is CursorReport regardless of params, and it is checked BEFORE the private-marker check (L202-210). So '\x1b[?12;40R' is CursorReport (test L557) and '\x1b[1;2R' (shift+F3 on some terminals) is also CursorReport. That is also why the CSI F-key arm is only `b'P' | b'Q' | b'S'` (L231): S gives F(4), and there is no CSI F3.
- decode_csi terminator scan (L192-195) starts at index 2 and looks for 0x40..=0x7e. Bytes outside that range, including ESC, are skipped as params, so '\x1b[1\x1b[A' is one Unknown of length 5 (fin '['), then Char('A'). No terminator gives Unknown with len = rest of chunk (L197; test L599-601).
- CSI params (L212-217): non-UTF-8 becomes "", and an empty or unparsable param becomes 0. The vector is never empty, so `p[0]` (L244, L256) cannot panic. The modifier is `p.get(1).unwrap_or(1).saturating_sub(1)` with bits 1=shift, 2=alt, 4=ctrl, 8=meta. Higher bits (caps/num lock 64/128) are dropped. CSI-u with a 0 or missing code (e.g. '\x1b[u') gives Char('\0'), because char::from_u32(0) is Some.
- CSI Z (L232-243) forces shift on top of the parsed mods. Stray '\x1b[200~' is only intercepted at the Decoder level (L79) and in the ESC-ESC guard (L156); a stray '\x1b[201~' outside a paste decodes as Unknown(6).
- scan_paste (L99-114) restarts a partial match with `usize::from(b == 0x1b)` on mismatch. That is correct for this pattern (one ESC), and the end marker is matched across chunks via `paste: Option<usize>`. Bytes inside a paste ('\r', '\t') are never keys (test L613-622). The whole remaining paste region of a chunk is ONE Paste event (L74-78).
- Decoder state handling in pty depends on the decoder living next to the hold logic. on_keys appends chunks to `held` WITHOUT decoding while held is non-empty (pty.rs L1030-1032). It resets the decoder when it starts holding (L1069, 'held bytes start outside a paste and are decoded again'). release_held replays the raw held bytes through on_keys from Pty and timer events too (L764, L888, L1220), not just Stdin. Decoding once in the driver per Stdin chunk would advance the paste state on held chunks and decode them twice, and after a held paste start it would swallow later keys as Paste.
- Keymap::lookup is only consulted when `prompt` holds (pty L1049-1053). Binding::Ignore has no arm of its own: it falls through the `_ =>` arm to forward/ghost (L1079). Turning that match into exhaustive arms without `_` (plan section 1 rule) must keep guard evaluation order: Action if intercepting, Unknown if intercepting, `_ if tab_show`, Show/Toggle if global, then the rest.
- Mods equality is used as 'no modifiers' (pty L939, L1057, L1095: `key.mods == Mods::default()`), and meta is part of Eq. A Modifiers redesign must keep derived PartialEq over all four flags and Default = all false. Key must stay Copy (`let key = ev.key`, L1043).

## Plan gaps
- Phase 7 moves pty::ghost_key into ghost_text's GhostText (glossary: 'replaces pty::{ghost_key,...}'; Phase 7.1 moves ghost_keys_and_words). ghost_key takes &Key/KeyCode/Mods, which are still in crate::keys during Phase 7 and in dropdown after Phase 8. Section 2 does not allow ghost_text -> dropdown. Options: keep ghost_key in terminal_session's KeyRouter (only next_word/ghost_rest go to GhostText), put Key/KeyCode/Modifiers in shared, or add the dependency edge.
- KeyEvent (L46-51) is not placed. On_keys becomes KeyRouter (domain) plus HandleKeystrokesUseCase (application), and both need each key's byte range to forward or hold exact bytes. Application and domain cannot import terminal_session/infrastructure (fitness rules 1-2), so KeyEvent must become a domain VO, or the use case must take raw bytes and own the decoding.
- The Decoder in infrastructure conflicts with where it is used. The event table says the driver decodes Stdin. But the decoder reset (pty L1069), the undecoded append while holding (L1030-1032) and the replay of held bytes from Pty/timer use cases (L764, L888, L1220) need the decoder inside TerminalSession/EchoHold or behind a port. Following the table literally changes paste and hold behaviour. The decoder is pure std, so the simplest fix is a terminal_session domain service, or a KeyDecoder port that the session owns.
- keymap_defaults_and_overrides cannot move to dropdown/domain/value_objects/keymap.rs as 'keys.rs tests' (Phase 8.1) suggests. It needs the decoder (terminal_session infra, reverse dependency) and serde_json (fitness rule 1, unless #[cfg(test)] is exempt; the plan does not say). Keep it verbatim in stdin_key_decoder.rs, or split it.
- The fitness test (section 1) does not say whether #[cfg(test)] code in domain files is scanned. The keys.rs test helper `settings()` (L665-670) uses serde_json. After Phase 2, Settings::from_map(serde_json::Map) probably no longer exists, and the helper cannot import settings infra (rule 3). The test needs a domain-level Settings builder from SettingValue (e.g. a cfg(test) from_pairs). The plan only gives Settings the getter surface.
- Section 4 lists `key, key_action, key_binding, keymap` but not KeyCode and Modifiers. Either add key_code.rs and modifiers.rs, or allow them in key.rs; both are pub(crate) and widely used, so the 'small private helper' exception does not apply.
- 'Domain struct fields are private' clashes with how Key/Mods are used. The decoder in another module builds and mutates them (L159, L184, L218-223, L236), pty builds Mods literals (L166-176), and the tests use const struct-update (L455-466). The plan does not specify the constructor or setter API; it needs const fn constructors to keep the test consts.
- Phase 8.1 creates terminal_session/infrastructure/adapters/ before Phase 9, while pty.rs (legacy, unregistered) imports it. That is fine for fitness rule 3 only while pty.rs is not a registered module. Note it so Phase 8 does not register terminal_session early.
- Phase 2.2 says Settings defaults come from the catalog, and the catalog has the template entry 'autocomplete.keybindings.<keystroke>' with default "" (settings.rs L307-312). If the new with_prefix also yields catalog defaults, Keymap gets ('<keystroke>', ""). That is harmless today (the parse fails and it is dropped), but with_prefix should keep iterating user-set keys only.
- Phase 11 removes `#![allow(dead_code)]` (main.rs L3) and deletes whatever the compiler flags. The free `decode()` (L55) is used only by tests, so it would be flagged and deleted, breaking 5 tests. Mark it #[cfg(test)], or have the tests call Decoder::default().decode(..), which is pure restructuring.
- Plan section 4 terminal_session lists key_tester_command ← cli::key_tester/key_line. That code does not use keys.rs (it prints raw bytes), so it does not depend on the stdin_key_decoder move.
- Phase 8.1 calls it `KeystrokeParser`. In Rust this should be a free fn in keystroke_parser.rs, not a one-method struct. normalize is listed there too, but Keymap::lookup (a VO) needs it, so Key::normalized() is the less surprising home.
